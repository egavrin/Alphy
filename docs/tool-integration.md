# Native mini-app integration

`ToolGenerationService` serves the chat and library entry points. It uses an injected `ChatProvider` and a request-specific `CloudSession`. Requests contain the current prompt and confirmed images. Refinement includes the current schema and program. Private record or capability-result artifacts omit live state, initial defaults, and UI from that request. Generation does not reuse chat history or old image references.

`ToolSpec` accepts artifact protocol 3. Earlier protocols remain stored with their data intact but cannot execute. The definition includes a bounded state schema, initial state, native UI, one JavaScript function body, and declared capabilities. Optional fields declare private collections, typed capability results, and at most four identified drawing surfaces. `ToolUiCatalog.modelGuidance()`, `ArtifactProtocol.modelGuidance()`, and `CapabilityCatalog.modelGuidance()` supply the implemented generation catalogs.

The optional field `appFile` holds the app file of an app that the kit built (`kit/README.md`). A voice screen stores a template file in `appFile`. The kit expands that file each time it compiles the app, such as for the save of a change, the restore of an earlier version, or a manual edit.

State supports scalar values and bounded lists, objects, and arrays. State has a 48 KiB limit. Mini-app definitions have a 256 KiB limit. JavaScript source and native UI each have a 64 KiB limit. Native UI also has a limit of 512 structural nodes, depth eight, and 2,048 units of aggregate rendered work. Sandbox requests have a 64 KiB limit. Sandbox results have a 192 KiB limit. Native controls include typed forms, semantic containers, row templates, charts, motion, and bounded perspective layers. The contracts reject unknown fields and invalid bindings.

Each app has its own color scheme. `theme.palette` selects one of 11 curated palettes in `ToolPalettes`: `graphite` uses the Alphy scheme, and the other ten are Material schemes that `tools/palettes/generate.mjs` makes from fixed seed colors. Without a palette, the `theme.preset` value selects one. `theme.dark` set to true makes a dark app. Otherwise, the system light or dark mode applies. Text, styled containers, and drawing commands share six roles: `default`, `muted`, `accent`, `success`, `warning`, and `error`. The `success` and `warning` roles stay green and amber in every palette. When the root node is a theme, the full view uses the app colors around the app too: the top bar, the margins, and, when the app fills the screen, the system bar areas. A saved definition with `theme.mode` stays in the library with its data and version history. Its controls cannot run. The user can explicitly delete it.

Icons come from the shell glyphs and from Lucide 0.460.0 (ISC license, `assets/licenses/lucide.txt`). `tools/icons/generate.mjs` converts the selected Lucide files into the stroke paths of `ToolIcons`. Icon nodes, buttons, cards, list items, metrics, badges, chips, banners, and empty states accept an icon name from `ToolUiCatalog.icons`.

One artifact handler receives native actions, lifecycle events, identified surface events, subscribed frames, and subscribed timers. When a press ends a frame or timer subscription after the drawing host read it, the coordinator drops the late frame or timer event: the handler does not receive it, and the drawing continues. Native frame requests follow the display clock. Generated simulations use `dt` rather than a fixed frame rate. Drawing supports bounded shapes, paths, gradients, and affine groups. The canvas uses the shell surface color. Solid fills and gradient stops accept role names, tones of a role, `#RRGGBB`, or `#AARRGGBB`. A tone is a role with a step from `+1` to `+3` or `-1` to `-3`, an alpha `@0` to `@100`, or both, such as `accent+1@40` (`GraphicsContract.toneOf`). A step mixes the theme color of the role with white (30 % for each step) or black (25 % for each step), so a tone follows the theme. The kit draws its path, arrow, and arc kinds, its glow, opacity, and turn properties, and each library line as these paths, gradients, and groups (`kit/README.md`, section "The library"). Use roles for scene text and frames. Drawing limits apply to the retained union across surfaces.

Frame, pointer, timer, and control evaluations use a fixed 100 ms asynchronous watchdog. Other evaluations use 500 ms. The monotonic cutoff starts before native submission and includes execution and asynchronous result completion. Both retained sessions and disposable smoke use these limits. Timeout closes the isolate and rejects its result without an event retry or a state or effect commit. These limits do not measure script CPU time or guarantee a displayed frame rate.

Generation validates a candidate before acceptance. Each disposable sandbox branch uses the ordinary transient slot. The branch closes its lease in `finally`. It does not replace the foreground retained lease. Preview and render must preserve the input state. A separate branch opens the candidate and exercises every declared surface, pointer transitions for both pointer IDs, both control directions, subscribed frames and timers, and start, pause, resume, restart, and stop events.

Each available control receives representative valid typed values. Samples include current values and bounded alternatives, the first and last selection options, and the first and last collection rows. Row templates use current stable keys. Each independent action branch starts with the disposable initial state and a new transient lease. The production action validator checks each action. The production result validators check every returned state, UI, drawing, subscription, effect request, and record request. Merged drawing also receives aggregate validation before the next smoke event.

Smoke validates requests without executing them. It has no store, capability broker, launcher, provider, scheduler, permission, or grant interface. It never creates capability or record result events. A pending effect or record request ends that action branch. The accepted preview retains its original validated state. Open, action, frame, pointer, timer, and lifecycle smoke state never becomes accepted state.

New app generation permits three repairs each for PLAN and COMPLETE. A repair patches a usable candidate or uses the stage's one full rewrite when no usable candidate exists. Generated script errors, execution timeouts, and invalid results enter that flow. The diagnostic records structural paths, step and slot numbers, and event kinds. Diagnostics exclude live values, generated IDs, and raw exception text. The repair request also includes the rejected candidate. Infrastructure failures such as a busy transient slot return directly. Cancellation preserves the prior artifact and its records, grants, and revisions.

`ArtifactCoordinator` serializes runtime transitions for an artifact and its surfaces. Revision and state tokens reject stale commands. Only frame and pointer-move publications use coalesced persistence. Native actions, result deliveries, private records, and effects retain guarded commits. Pending native work fences autonomous events. No failed native effect receives an automatic retry.

A drawing surface whose open meets a busy retained slot waits with no bound while it is on the screen and resumed. It tries again about every 5 s and shows «Запустится, когда другое мини-приложение остановится.» with no red line. It keeps its last drawing, or an empty canvas when it has none. Any other failure of an open tries three more times, one second apart, before «Сеанс остановлен. Откройте мини-приложение снова.» and «Повторить» show. A failure after the first drawing shows the line at once. The tries stop when the surface leaves the screen. When a newer revision of the tool is saved, the surface of the old revision stops with no line, and the canvas keeps the last drawing of the tool until the new revision draws. Each exception that a surface drops writes one `AlphyGeneration` log line with the exception class, its code, and the next step (`wait`, `retry`, `stopped`, `replaced`, `input`, or `save`), never its message. A wait for a busy slot writes one `wait` line when it starts and one `surface javascript_busy opened` line when the open succeeds.

The dialogue stage of the voice mode draws a stage preview while the reply of a template call arrives (`docs/voice-integration.md`). During a change of the app on the stage, the host still makes the previews, but the stage does not draw them over the dimmed app. A stage preview is a compiled app that is not stored. It stays in memory (`ToolController.stagePreviews`), with no store row and no draft row. The call gives each text delta to a buffer on the thread that reads the reply, and it never waits for an update. A loop takes the newest complete lines when its last update ends, so a slow device gets fewer updates. Each update runs the kit preview step in a new transient isolate with a deadline of 1000 ms (`APP_FILE_PREVIEW_MS`). Smoke runs only for the final app, never for a preview. A busy transient slot, the deadline, or a step that gives no preview skips that update. The loop ends when the reply ends, and the final compile waits only for the update in flight. So no update holds the transient slot during the final compile and the host check.

A template scene moves and changes smoothly on the canvas (block 2 plan, stage 7, `tools/SurfaceGlide.kt`, `tools/NativeToolSurface.kt`):

- The clock of motion. A `play` scene of the kit moves its value with a timer of 50 ms (`ANIM_MS` of the kit run-time). Each timer event is one app call. A step of the motion of a kit scene writes no record: a press (also the pause) and the close of the stage write the state (stage 7, fix list 1, F1). On the emulator a step comes about each 80 ms (62 steps in 5 s), and its app call takes about 10 ms. Between two drawings of a step, the host draws each display frame itself, with no call into the app: each number of the same list of shapes moves linearly over the time of the step before it (16 ms to 250 ms). A number that jumps more than a quarter of the surface in one step (the wrap of a loop from its end to its start) shows at once. The gate C1 counts the pictures that the stage draws (`SurfaceFrameMetrics.Snapshot.pictures`): at least 30 different pictures each second for 5 s of the orbit scene with images (`StageMotionWorkflowTest`).
- The glide of a change (M5, M6). A change of the drawing that a press makes glides with an ease-out. Its glide ends 250 ms after the press (`SurfaceGlide.pressed`, which the tap of a control and a spoken press call), and it runs at least 120 ms, so the time of the app call is part of the glide. The state counts at once: only the picture glides. A shape whose kind, color, or text changes cross-fades alone, and a drawing with another list of shapes cross-fades as a whole. A second change during a glide starts from the picture that shows at that moment, and the last frame is the new drawing itself. The gate of M5 is at most 300 ms from the press to the last frame (`SurfaceFrameMetrics.Snapshot.glideEnds`). Only a template scene glides (an app file that starts with `scene(`). A free app draws each drawing as it comes.
- A press on a running kit scene (F1). The controls of a stage app look disabled while the controller runs a press, as in Alpha 22, so a control never looks ready while it ignores a tap. A press of a kit scene takes 96 to 242 ms of busy time. Known stall: the access read of `ToolController.loadSnapshots` opens a fresh store, and its open can wait for a write lock while it holds the library gate. A press can then wait 0.5 to more than 2 s. Stage 7 does not change the store.
- A diagram of the kit walks the parts of a ready object of the library. A thing with no ready object gets steps, as in Alpha 22. The play row of a kit scene shows only when the scene has no control line. Beside a control, the motion runs with no play row, and the shown screen has no `motion` (`kit/README.md`).
- A spoken press of a step (the narrator, the classifier, the routing, and the follow call) waits for the ready stage and tries again until the step shows, for at most 4 s (`LiveVoiceBridge.press`, fix list 2, H2). The set of a step is idempotent, and a press that did not run changed nothing. A toggle, such as the pause, runs one time. Each lost press writes one warning with the tag `AlphyPress`, the action id of its control (no text of the screen), and its cause: no control, stage not ready, refused by the controller, or the step did not show.
- The draw of a frame uses one `Paint` for the images of each pass (`drawSurfaceLayers`). A layer of a cross-fade draws in `saveLayerAlpha`, and the new picture of a whole cross-fade first fills its surface with the canvas color.
- A scene that no person sees does not run (C7). The session of the surface runs only while the stage is composed and the activity is resumed (`repeatOnLifecycle(RESUMED)`), and a covered stage gets no timer event. So the timer of the motion stops when the stage leaves the screen, and no app call runs. When the stage is back, the open event of the kit computes the value from the clock, so the motion goes on at the place where its round is at that time.

The stage and its app are one surface. `NativeToolUi.kt` draws a stage app and a stage preview with the stage flag of `NativePreset`, which a `dialogueTitle` sets. With the flag, the theme of the app takes the shell surface color for its background and its surface. So the stage, the app, its canvas, and each part in the surface color have one color. Cards keep the containers of the palette. A dark app (`theme.dark`) in a light shell keeps its dark surface, because its text is light.

On the stage, the card of a failed request shows a fixed text for the group of its error code, in place of the error text of the message (`stageError` in `ui/DialogueStage.kt`, the `errorText` parameter of `ChatMessageItem`). Each text says what the person can say next. The strings are in `app/src/main/res/values/live_voice_strings.xml`. The first group that matches applies:

| Group | Error codes | String | Text |
| --- | --- | --- | --- |
| Key | `KEY_ERRORS` (`cloud/CloudKey.kt`) | `stage_error_key` | «Нужна настройка сервиса ИИ. Нажми «Открыть настройки».» |
| Search | `search_no_usable_results`, `source_attribution` | `stage_error_search` | «Поиск не дал ответа. Скажи «попробуй ещё раз» или спроси по-другому.» |
| Image | `image_generation` | `stage_error_image` | «Картинка не получилась. Проверь картинки в настройках «Сервис ИИ» или спроси без картинки.» |
| No answer | `LiveVoiceBridge.NO_ANSWER_CODES`, and each `http_<status>` code | `stage_error_no_answer` | «Сервис ИИ не ответил. Скажи «попробуй ещё раз».» |
| Too big | `LiveVoiceBridge.TOO_BIG_CODES` | `stage_error_too_big` | «Это не помещается на один экран. Скажи короче, одной фразой.» |
| Other | each other code | `stage_error_other` | «Не получилось. Скажи «попробуй ещё раз» или спроси по-другому.» |

The key group comes first, because `auth` is also a code of no answer. The card of a key error keeps its «Открыть настройки» button. The no-answer and too-big groups use the codes of a failed full generation (`LiveVoiceBridge.fullFailed`), but the voice gets its own host line for that failure (`docs/voice-integration.md`).

With an app on the stage, the routing call and the grounded decision of a spoken request get the shown screen as untrusted data (`ShownScreen.line()` in `tools/ShownScreen.kt`). The line is `ShownScreen.PREFIX` and one JSON object with `title`, `appFile`, `controls`, and `values`. `controls` holds the labels of the buttons and choice options that the host accepts as a tap now, only for an app with no capability that is not a 3D scene. `values` holds `{"control": LABEL, "value": V}` for each bound input with a label, in the order of the UI. An input is a catalog component that binds a value, requires an action, and is not a container or a video. A choice gives the text of its selected option, not the stored option value. An input in a row template gives no value. `values` also comes from an app that takes no press, and the line leaves it out when it is empty. The routing instructions say that SHOWN_SCREEN holds the present value of each control (`ChatToolReply.shownScreenInstructions`).
A steps scene adds `step`: `{"index": K, "count": N, "label": STEP}` of its first choice, from 1 (`SceneStep`). The line has `actions` when the stage app has some: the last three actions on it, oldest first, each `{"who": "tap" | "voice" | "narrator", "control": LABEL, "value": V}` (`SceneAction`, from `LiveVoiceBridge.actions`). An app with private results gives no `actions` and no `step`. The step and the actions stay when a long line drops other fields.

The narration of a new template scene (`say` or `say1` to `sayN`, `kit/README.md`) comes after the card. When the reply holds the card, the host compiles the lines before the narration, stores that app, and turns its controls on. The rest of the call goes on (`TemplateStream.narration`). At its end, the host saves the narration into the stored `appFile` at the same revision and state (`ArtifactCoordinator.saveSpec`), and the trace marks `narration_saved`. A later revision, an archive, a cancel of the request, a deleted app, a failed call, or the end of the voice mode drops it, and the trace marks `narration_dropped`. The call is paid, so a fallback of the run, a cancel of the request, a deleted app, the end of the voice mode, and the store of a new revision stop it before its end. A narration line before the card holds back the store until the call ends. `ToolController.savedNarration` gives the saved narration of a revision only until the list of tools holds it. A new revision or a delete ends it.

An app with private results gives no `values`, because a model request never gets its data. Its spec can mark it (`ToolSpec.privateResults`: typed capability results, collections, or a navigation or owned calendar capability). The store keeps that mark after a later change of the spec (`ToolController.privateResults`, the table `capability_private_owners`). A line longer than 8,000 characters (`ShownScreen.MAX_LINE`) drops the app file first, then the controls from the end, and last the values from the end.

The routing decision of a spoken request with the kind `screen` on offer also has the required field `family`, `explain` or `data` (`ChatToolReply.screenFamilies`). The routing instructions set `data` for a screen of values side by side: a comparison of two or three things, a table of a set of things, or a chart of numbers, and also for a request to show the present subject as a table, a chart, or a comparison (`ChatToolReply.FAMILY_RULE` in `voiceScreenInstructions`). A `refine` keeps its family too, and each other kind decodes as `explain`. `Decision.isData` is true only for a data screen. The follow call of a voice-only turn names the family of its screen with the same sentence (`CloudEvent.Follow.family`, `FollowDecision.Screen.family`), and a follow screen of the family `data` runs the data call with no search. `ChatToolReply.encode` writes the family only when it is `data`.
A data screen gets no early plan call. After the routing call, `ShellViewModel` sends one data call with the section "Template data" (`AppFilePrompt.templateData`) and, after a search, the host check of its sources (`DataCheck.of`: the title and the summary of each source, the site name or host of the first two sources, and the search time). The sandbox runs the check in the kit (`kit/README.md`, section "The data family"). A rejected form is stored as a nodata card, and the trace marks `data_rejected`. A spoken change of a data form on the stage is a new data call with the shown screen. So is a `refine` of the family `data` of another stage app, such as an explain scene shown as a table.
A `table` node may bind its marked row key with `selectedKeyBind` (it needs an `action`), name the column of the marked cell with `markColumn`, and show at most `visibleRows` rows (1 to 50) before its rows scroll inside the box. On a compact width (smallest width under 600 dp) the host shows at most 6 rows, so that a data form at its caps does not scroll the page. A marked row under the shown rows scrolls into the box. A `chart` node may have an `action` and bind its marked category with `selectedKeyBind`. A tap on a row or a point sends its key or category as the payload, and the host accepts only a current key or category. The marked row and cell, and the marked point, have the selected semantics. A chart of 8 points or fewer shows the label of each point.
The look of the data nodes uses the roles of the color scheme only, so the dark theme works (stage 5 look). A table is one box with a 16 dp corner and a quiet head. A column where each cell starts with a number aligns to the right, its head too. A number stays on one line: its column is as wide as its longest number, and a text cell can take two lines. When the columns do not fit the box, the cells use the small text style with less padding, and when they still do not fit, the table scrolls sideways. A marked row has the container tint, and its marked cell is a pill in the accent color. A fade at the bottom edge shows rows under the box. A table node with `variant: "compare"` and one sign for each thing (`signs`) is a comparison: a head cell for each thing, then a block for each row with its label, the values, and a bar under each value. A bar is the share of the largest number of its row, and a row with a value that has no number has no bars. A bar or line chart sits in its own card, with the value of each point, a zero base for bars, and 15 % of the range free under and over a line. The label of a chart point shows an integer of 5 or more digits with a thin space between groups of three. A table shows each cell as written, because its digits can be a code: the kit groups the numbers of a data form in the compiled rows. A text with `variant="source"` is a small muted line with a link icon.
In the shown screen, each row of a table with an action and each category of a chart with an action is a control, with the label `TITLE: KEY`. A table or a chart with `selectedKeyBind` gives its marked key as its value.

The follow call of a voice-only turn (`docs/voice-integration.md`) has one strict function tool, `submit_follow_decision` (`ChatToolReply.SUBMIT_FOLLOW_DECISION`), and the request forces it. Its schema (`ChatToolReply.followSchema()`) is an object with no other properties and four required fields:

| Field | Type | Meaning |
| --- | --- | --- |
| `kind` | string, one of `none`, `screen`, `mark`, `press`, `clear` (`ChatToolReply.followKinds`) | What the stage does after the turn. |
| `brief` | string | For `screen`: the brief of the new scene. Empty for the other kinds. |
| `target` | string | For `mark` and `press`: the label of a control of the shown screen. Empty for the other kinds. |
| `answered` | boolean | True when the words of the voice gave the answer. False when they only promised it, such as a short waiting line. |

`CloudProvider` accepts only a reply with exactly these fields and a known kind. Any other reply is the failure `tool_invalid`. `FollowDecision.decode` turns a `screen` with a blank brief, or a target that names no control of the shown screen, into `none`.

`Message.spoken` marks the two messages of a voice-only turn. `ShellStore` writes it as the field `spoken` of the message JSON and reads it with `optBoolean`, so a message with no field is not spoken.

`ToolStore` retains accepted tools, revisions, drafts, collections, grants, and native result receipts. Acceptance commits the candidate and removes a standalone draft in one transaction. A chat-linked save retains its draft as a receipt so Alphy can recover an interrupted card write. Rejection removes only the selected draft. Refinement preserves existing field types, collection schemas, stable IDs, and saved values. Rollback creates a revision only when its schema accepts the current state.

`ToolController` exposes the workflow to Compose. Chat cards, the library, the focused app, widgets, and automations use the same artifact contracts. Generated JavaScript has no direct network, files, credentials, Android APIs, imports, or generated Kotlin. Native capability execution requires the declared contract, Android permissions, and the applicable selection or approval. Network requests also require per-app consent.

Smoke is a bounded deterministic sample. It does not prove arbitrary user sequences, real provider results, displayed frame rate, or hardware touch latency. Root acceptance verifies those requirements separately.
